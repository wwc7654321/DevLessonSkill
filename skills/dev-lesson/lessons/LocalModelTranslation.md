# 本地小模型翻译（文本）经验

适用：调用本地大模型（LM Studio / Ollama 的 OpenAI 兼容接口）批量翻译文本（游戏对话、小说、字幕等）。重点在工程化保障，与具体文件格式/游戏无关。Godot 打包见 [[GodotGameMod]]。

## 〇、先分清两个场景（策略与风险完全不同）

- **场景一 · 有中文旧译（校对/改写）**：输入 = 原文 + 现有译文，任务是纠错/润色。最大风险是**照抄参考译文 → 全量空转**（输出==输入、0 处改动），对策见第八节。
- **场景二 · 整体重新翻译（从零翻，无中文旧译）**：输入 = 原文（+上下文）。最大风险是**格式损坏（占位符/假名/变体结构）与术语漂移**，对策见第三~七节。含两个子场景：
  - **2a 纯净重翻**：只喂原文（+上下文），无任何参照。
  - **2b 多语言参考**：额外喂官方英文列等中立参照（见第五节），能压住零代词/授受/使役的主语方向混淆；参照≠照抄，仍以原文为准。

判断清楚再选 prompt 与校验；两套可共存，但别拿场景二的校验直接套场景一——场景一漏了「输出 ≠ 旧译」这条照抄探针。

## 整体逻辑（脚本骨架）

读文件逐行取原文（先预过滤：`ja` 为空、或 `ja==zh` 且无假名的行直接跳过）→ 组装 prompt（静态指令放 `system_prompt`，原文+上下文+旧译放 `input`）→ 调模型 → 校验译文 → 立即写结果缓存。核心是把**校验 + 断点续传**做进循环，小模型输出不稳，翻坏一条不能拖累全量。

## 术语表管理

术语漂移的解法是维护一份术语表，随翻译请求一起下发。要点：

- **基础词锁定**：角色名、称呼（哥哥/主人）、核心道具等，写死在表里，不参与自进化覆盖。
- **自进化**：每翻 20 句，把最近的「原文→译文」对喂给模型，让它提炼新术语合并进表。
- **提炼规则**：只挑游戏特有、模型易译错/译得不一致的词（角色名、称呼、专有道具、易歧义固定说法）；排除通用词（攻击、防御、确认这类普通译员就能一致翻的）；排除日文=中文的无价值条目。
- **上限与淘汰**：术语表严格限条数（如 40 条）和字符数（如 200），超限按 FIFO 淘汰非锁定词，防止 prompt 无限膨胀、拖慢每轮请求。

## 一、API 约定（LM Studio OpenAI 兼容）

- 请求体 `{"model","system_prompt","input","temperature"}`，不是 OpenAI 的 messages 数组。
- **空 `input` 会被拒**（`input must not be an empty string`）：静态指令放 `system_prompt`，动态内容放 `input`，保证 input 非空。
- 响应在 `output[]`，取 `type=="message"` 那条的 `content`。
- **模型没加载完就测会大量返回 None（假失败）**：先单发一条确认通了，再重测之前"失败"的串。

## 二、批量 vs 逐条

- 逐条每条都重发完整 system_prompt，重复开销大；**小批量（同文件相邻行合并，BATCH_SIZE≈4）省请求数和重复 prompt，吞吐约 2~3 倍**。批次太大模型会漏翻/串行/格式崩坏，先小批量测质量再定。
- 批量输出用 `@@数字@@` 标记分隔，正则 `@@(\d+)@@\s*(.*?)(?=@@\d+@@|$)`（DOTALL）解析；某条校验失败只回退该条，整批解析失败回退逐条。

## 三、必做的校验（缺了会出脏数据）

1. **占位符**：`%s %d %.0f %%` 数量/种类与原文一致（正则 `%%|%[-+0-9.#]*[a-zA-Z%]`）。
2. **残留假名**：译文不能再含日文假名字母。
3. **断点续传**：每句结果立即写 jsonl cache，重跑跳过已完成项。
4. **标记语法结构**：译文含任何标记语法（`[[a|b]]`、`<tag>`、`{0}` 等）时，校验结构完整性——分隔符数量、闭合标记是否齐全。**光查假名残留查不出结构损坏**（如 `[[a|b|c]]` 被截成 `[[a|b]]`，或丢闭合 `]]`）。

## 四、假名检测区分「假名字母」和「标点/结合符」

- `・`(U+30FB)、`゛゜`(U+3099-309C) 不是"未翻译假名"；把 `・` 当残留会让正常格式串（`单价+30%・传送带+15%`）被反复重试→回退旧译。
- 残留正则只留真字母：`[ぁ-ゖゝ-ゟァ-ヺー-ヿㇰ-ㇿ]`。
- 输出后可先剥掉浊音符（`゙゚゛゜`）再校验。

## 五、上下文与中立参照（英文列）

- 上下文 = 同一文件里该行的**前一行/后一行**（prev/nxt），拼进 `input` 帮模型消歧。窗口取前后各 1~2 行，**且只给对话类文件加**；孤立 UI 串不加（加了反而引入无关语境，如 `ベルト` 会从「传送带」错翻成「腰带」），旧译已正确就保留。批量模式可省上下文提速，硬串失败再回退逐条（带上下文）兜底。
- 若游戏有官方多语言列（如英文），可拿**英文列当中立参照**拼进 input，比中文旧译可靠（不会被同语言旧译带偏）、比带全文上下文便宜。**尤其能压住日语零代词/授受/使役的主语方向混淆**——英文把主宾写明了（`手伝わせて` → `Let me help you`）。注意是"参照"不是"照抄"：英文也可能意译或有错，模型仍以日文原文为准。

## 六、模型选择

- 多模型 A/B：固定样本（含硬 case：拟声词、长格式串、黑话、**授受/使役的主语方向**——谁对谁做什么，如 `手伝わせて` = 让我帮你，主语宾语全是零代词、全藏在动词形态里）+ 记样本数/并发/总耗时/每条耗时，温度 0.3 左右，选质量/速度平衡的。
- 不同模型不能同时驻留显存，让用户手动卸载/加载。

## 七、用户约束「翻译必须走模型」

- 用户可能要求译文全经模型生成。手工清理残留标点/结合符（删中文里不该有的 `゛`）属"码点清理"而非翻译，可做；整句改写/选词必须交给模型。模型反复翻不干净的硬串，优先回退到完整旧译（完整性 > 措辞更好但被截断）。

## 八、场景一（有中文旧译/校对）：警惕「照抄参考译文」空转

- **症状**：把旧译文当"参考译文"喂给小模型做"校对/改写"（温度 0.3 左右），结果输出 == 输入，一字不改。曾因此全量 4710 句重翻**实际 0 处改动**，等于白跑（断点缓存里全是旧译，游戏仍是机翻）。术语提炼等"生成式"提示词在同一模型上却正常出新词，说明不是模型没加载，而是"校对"提示词 + 低温触发了照抄。
- **必做校验**：重翻/校对跑完后，**显式统计「输出 != 旧译」的行数**；若 ≈0，说明空转，别误以为"机翻本来就翻得对"（拿一两个已知错句当探针即可识破）。
- **对策**（按需选一；后两条其实是"转去场景二"）：
  1. 仍留在场景一：提示词显式加"逐句审读改写，不要偷懒直接照抄；判断无误的可保留原样"，并适当升温度。
  2. 转场景二-2a：不喂中文旧译，只喂原文（+ 上下文），纯净重翻。
  3. 转场景二-2b：用官方英文列等中立参照代替中文旧译，避免被同语言旧译带偏。

## 九、场景一（校对）：定向修补优于全量重翻

- 若只想修某一类错误（如日语主语方向），**不要全量重翻**：先按语法特征正则筛「风险行」（使役 `させて/させてくれる`、授受 `てくれる/もらう/あげる`、被动 `される`、愿望 `たい/ほしい`），只送风险行给模型，其余行保留旧译不动。全量重翻会引入大量无谓改动（实测 56%）并产生新错译（如 `お仕事がんばってね`→「咪伊也要努力工作哦」，把工作错安给女主）。
